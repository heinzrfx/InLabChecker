# Sondagem para o header: margem do rollout e alpha do PNG

Build: 3ds Max `#(26000, 64, 0, 26, 2, 14, 20518, 2024, ".2.14 Security Fix")` (3ds Max 2024.2.14). Data: 2026-09-22.

MCP: `get_bridge_status` confirmou `"connected": true`, `"maxVersion": 2024`, `"safeMode": true`, pid 13576, transporte namedpipe. So a instancia 2024 estava conectada; 2027 nao foi verificado (fora do escopo desta tarefa).

**Nota sobre o metodo:** o `format` dentro de `on ... open do` nao volta no resultado do MCP (`execute_maxscript` devolve so o valor de retorno do script, nao a saida do listener). Alem disso, uma variavel de rollout criada com `createDialog` em uma chamada MCP — mesmo declarada com `global` — nao sobrevive de forma confiavel ate a proxima chamada separada: `isKindOf <rollout> RolloutClass` voltou `false` na chamada seguinte, mesmo com a janela nativa ainda aberta. Por causa disso, toda leitura de estado foi feita dentro da MESMA chamada que cria e abre o dialogo (criar, ler, devolver o resultado como string, fechar), nunca em uma segunda chamada dependendo da variavel sobreviver. Isso deixou dialogos orfaos (janela nativa aberta, variavel MAXScript perdida) em pelo menos 4 ocasioes — resolvido no Step 4 enumerando o desktop com `windows.getChildrenHWND` e fechando por `windows.postMessage <hwnd> WM_CLOSE 0 0`, ja que `destroyDialog` precisa da variavel que nao existia mais.

| Trava de arquivo | Sem trava. O script usou `local tmp = dotNetObject "System.Drawing.Bitmap" arte` (abre o PNG e prende o arquivo) seguido de `pb.Image = dotNetObject "System.Drawing.Bitmap" tmp` (copia pra um Bitmap novo, independente do arquivo) e so entao `tmp.Dispose()` (solta o arquivo). Confirmado por fora do Max: depois do dialogo aberto com a imagem carregada, `Rename-Item` no PowerShell sobre `%TEMP%\inlab_sonda_bulbo.png` funcionou sem erro ("rename OK — arquivo nao estava travado"). Isso importa porque `Image.FromFile`/`Bitmap(String)` sozinho mantem o arquivo aberto emquanto a imagem existir, e um PNG travado impediria o updater de renomear a pasta de instalacao (passo 5 do pipeline de atualizacao). Caminho a seguir nas tarefas 3/5: sempre copiar pra um `Bitmap` novo e descartar o original assim que carregar arte de arquivo. |

## Achados colaterais (pegadinhas, para registrar junto das outras de `fn_autouv.ms`/`fn_realworldfix.ms`)

- **`pnl.Parent` de um `dotNetControl` declarado direto no rollout fica `undefined`.** O MAXScript hospeda esse controle via `SetParent` nativo (Win32), nao via `Controls.Add` do WinForms — entao a propriedade gerenciada `.Parent` (e `.FindForm()`) nunca reflete esse parentesco. Pra saber a hierarquia real de janelas (e medir margem/posicao), usar a API nativa que o struct `windows` do MAXScript expoe: `windows.getParentHWND`, `windows.getHWNDData`, `windows.getWindowPos`, `windows.postMessage`. `pnl.Handle as integer` da o HWND de partida.
- **Global de rollout criado dentro de uma chamada MCP nao sobrevive de forma confiavel pra proxima chamada**, mesmo com `global` explicito — isso e do bridge/MCP, nao do MaxScript em si (dentro do Max, via `fileIn`, globals de rollout persistem normalmente). Qualquer sondagem futura via MCP que precise ler estado pos-`createDialog` deve ler tudo na MESMA chamada que cria o dialogo, e limpar dialogos orfaos ao final enumerando o desktop (`windows.getChildrenHWND (windows.getDesktopHWND())`, filtrar por classe `"MAXScriptDialog"` e titulo) em vez de confiar em `destroyDialog <variavel>`.
- **`format` dentro de `on <rollout> open do` nao aparece no resultado do `execute_maxscript`.** Só o valor de retorno do script (ultima expressao) volta. Pra ler qualquer coisa calculada dentro de um handler, gravar em uma `global` e devolver essa global como string no final do MESMO script.
